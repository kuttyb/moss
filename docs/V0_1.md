# Moss v0.1 — the Phase 10 usable-language milestone

**Release status:** Phase 10.6F.1 passes its correctness and performance gates.
Moss v0.1 is ready for review and explicit re-closure; it has not been re-closed
automatically, and Phase 15 has not begun.

Moss v0.1 is a statically checked language for writing ordinary value-oriented
code, functional data processing, and synchronous domain services. Phase 10
establishes the architecture; the next milestone is **Phase 15 — Dogfooding**:
write substantial Moss programs, identify real friction, and let actual usage
determine the next refinements. This document is a milestone description, not a
published GitHub release or tag.

## One semantic frontend, two execution engines

```text
Moss source → checker / structural specialization / READ-WRITE-CONSUME effects
             → closed ConcreteDomainGraph
                 ├─ SynchronizationPlan → production 2PL + borrowed READ views
                 └─ Fast Debug → deterministic direct interpreter execution
```

Domain instances and immutable `domainroutes` are composed in the initial `main`
prefix. A `message` blocks until its target handler completes. `reply` establishes
an independent value and terminates the handler. Incoming payloads are immutable
snapshots. Source `await` and `spawn`, self-send, same-domain handler chaining,
and ordinary storage/passing of domain handles are rejected. Active examples and
semantic regressions use synchronous `message` and static construction; the two
removed keywords remain only in focused migration-diagnostic source fixtures.
`tests/tooling/check_retired_syntax.py` enforces this corpus rule during `make check`.

Production uses one plan-driven Handler2PL backend at every optimization level.
Synchronization planning is compile-time only. Production Rust contains statically
generated typed synchronization classes and direct lock acquisitions. Each
instance owns its `RwLock<ClassState>` fields; no runtime plan is interpreted. A handler acquires exactly its ClassSet in
class-rank order, using SHARED/EXCLUSIVE modes, and retains guards through nested
messages until completion. Nested acquisition follows `(domain_rank, class_rank)`.
Ordinary READs borrow protected/immutable storage; explicit message/reply value
boundaries may copy. Unexpected failure/poison is fatal. For failure-free execution,
domain-local protected state is conflict-serializable. This is not a transaction
across a whole call tree; fairness, rollback, and globally ordered outbound effects
are not promised.

Fast Debug interprets checked Moss directly, including composition, routes, nested
messages, state mutation, and terminating replies. It produces deterministic
semantic traces with stable identities. It does not simulate locks, contention,
threads, or alternate schedules. All reachable Moss code must have source;
source-free `.mossi` providers remain a production facility.

## Structural traits and ordinary values

**Moss traits are structural compile-time predicates, not nominal memberships.**
A type need not declare that it implements a trait. Conformance is checked when
that type reaches a use requiring the trait. There is no `implements` syntax or
implied runtime trait object.

Ordinary function parameters have inferred READ/WRITE/CONSUME effects. WRITE
parameters write through to mutable caller storage, including primitives. No
parameter `mut`, `var`, `write`, or `inout` modifier is planned. Ownership transfer
and overlapping-argument checks are compile-time rules; ordinary READ does not
request an implicit deep copy.

## Modules, projects, and functional code

v0.1 has usable explicit modules/imports, project builds, typed exports, semantic
interfaces, and source-free production providers. The module system is usable,
not declared final: Phase 15 usage will determine further package/module ergonomics.
Use exported factory functions for provider-owned objects and concrete exports
where cross-module generic specialization is currently limited.

Functional/dataflow operators include statically specialized map/filter/reduce and
terminal operations. `-O0` retains eager execution; `-O` and `-Oshared-memory`
apply proven-safe functional rewrites and fusion. They all use the same domain
runtime. Fast Debug executes the current eager functional pipeline surface; `for`
traversal remains a production-backend limitation.

Start with the [ledger project](../examples/projects/ledger/README.md),
[index summary](../examples/dogfood_index.moss),
[data-cleaning pipeline](../examples/dogfood_pipeline.moss), and
[structural traits](../examples/traits.moss). These are seed programs prepared in
Phase 10, not the start of Phase 15 feature work.

## Intentional boundaries and known friction

- No recursion, runtime dynamic dispatch, trait objects, or user-defined generic
  syntax. Structural/static specializations cover the implemented callable slice.
- Static domain topology; current instances live for the enclosing program
  execution. No lexical domain-scope or dynamic thread/task ingress syntax.
- No finalized Rust interoperability or supervision/error-recovery model.
- No package/dependency resolver, general closure values, or explicit `deepCopy()`
  implementation. The standard-library and interpreter surfaces are still small.
- Exported provider fields remain private in generated Rust; factories avoid
  direct construction across module boundaries. Cross-module structural/generic
  specialization and some qualified statement-call forms still have limitations.
- Static aggregate accessors and provider bodies can increase generated code size.
  Explicit message/reply copies remain required value boundaries. F.1 removes
  runtime descriptor lookup, guard-map allocation, and generic take/restore;
  see its performance addendum for the remaining measured costs.
- Domain-heavy semantic traces grow with executed operations. Filtering/slicing
  beyond existing bounds remains future tooling work.

SynchronizationPlan is **graph-relative**, not a process-lifetime singleton
identity. Future concepts such as `DomainScope`, `DomainGraphTemplate`,
`ScopeActivation`, and `ImportedOuterRoute` remain breadcrumbs, not selected nested
scope semantics or current syntax.
